# 27 · 数据层库表设计 v9（`.kaogong.db` 单一事实源）

> 本文是 `src/shared/storage.ts` + `src/adapters/poolDb.ts` 的**设计依据与逐表说明**。
> 纪律：表/列的每一处存在都要能回答「**谁写、谁读、何时失效**」三问——
> 答不出来就是冗余列（v9 清理标准）。
> 本文与代码的对应关系由守卫 `SMOKE-KGDB-01`（表清单对账）与 `PAPER-SCHEMA-01`（列清单）锚定。

---

## 0. 三条设计原则（先于具体表）

1. **只有一个库**：一切数据（题目/卷/知识/用户态/管理台账/派生快照）都在 `.kaogong.db`。
   外源（16 仓库）只在**摄入期**被读取；运行期零外源 IO（I-DB-1，研究 26 §2.1）。
2. **按「可变性」分三组**，而不是按「业务模块」分：
   - `POOL_TABLES` 派生数据 → `rebuild` 清空后可从外源完全重建；
   - `USER_TABLES` 用户态 → 带 ws 维度，**rebuild 永不清理**（数据安全纪律）；
   - `META_TABLES` 控制面 → 历史事实（迁移台账/作业归档），**不可重建**。
3. **可扩展性靠「两条零 DDL 通道」**，而不是靠不断加列：
   - `user_kv(ws, domain, k)` —— 无固定形状的域对象（模考记录数组等）；
   - `entity_attr(kind, ref, k)` —— 任意实体的附加标注（人工结论/标签/笔记）。
   有明确维度的管理数据**必须建实体表**（可 SQL 诊断），不得塞进 JSON 桶。

## 2. 逐表设计要点（只写「为什么这样设计」，不重复 DDL）

### 2.1 `question`（核心宽表）

- **身份**：`canonical_id UNIQUE`，派生规则 `q:<qid>` > `cf:<content_fp>` > `fp:<fp>` > `h:<hash>`
  （独立命名空间的源带前缀 `q:<sourceId>:<qid>`，防跨源 id 撞库）。
- **`content_fp`**：跨源内容指纹。**必须含 img 区分因子**——图推通用题干剥图后会误并不同考点的题
  （实测 kadian 1895 → 925，误并 981 → 9 修复后归位）。
- **`source_extras`**：上游原始对象 JSON（末列追加）。派生列装不下的源特有字段全放这，
  这是「图推无损换源」的物理基础（cat/trap/acc/fmt/g 代码全保真）。
- **卷级列**（`score/requirement/reference/related_materials/paper_id/q_no/material_mid`）：
  **追加在末列**且由摄入侧**独立 UPDATE** 写入，**不扩共享 `QUESTION_COLS`**——
  位置参数错位一次就静默丢一列（cycle-40b/55 两次事故）。
- **索引**：`qid`/`fp`/`canonical_id`/`(module,category)`/`kadian`/`(source_id,local_key)`/
  `content_fp`/`paper_id,q_no`/`material_mid`，以及**部分索引** `ix_q_mat`（仅
  `group_material != ''` 的 18k 行进索引 → 材料组查询 735ms → 281ms）。

### 2.2 `wrong_book`（错题管理域，v9 实体化）

v8 只有「SRS 快照」字段；v9 补 6 个**可 SQL 诊断**字段：

| 列 | 为什么需要 |
|---|---|
| `canonical_id` | 错题与统一池对得上（回炉时可按需重取最新解析/五维） |
| `kadian` | 「我哪个考点最弱」必须能 GROUP BY（数组时代做不到） |
| `dims` | 五维标注快照（回炉时不必回池重取） |
| `first_at` / `lapses` | 遗忘曲线必需统计量（错 1 次 ≠ 错 3 次） |
| `srs_due_at` | SRS 调度的**物化结果**（可查询、可排序、可索引） |
| `last_result` | 「上次是对是错」——工作台筛选与诊断都要 |
| `origin_batch` | 补录来源批次（可追溯/可撤销；在线答错为 NULL） |

**主键 `(ws, sig)`**：ws 是第一隔离维度（R20 跨租户污染防线）。
**建表纪律**：v9 新列索引**必须在迁移函数里建**——写进 `SCHEMA_SQL` 会让旧库
`exec` 抛 `no such column`，整库降级（本轮实测 pool ready=false 的根因）。

### 2.3 `practice_session`（刷题管理，v9 新增）

一次练习/模考/回炉的会话头。**为什么需要它**：v8 只有 `study_event` 流水，
「今天刷了几个会话、哪个还没做完、平均耗时多少」无法回答（流水是事件不是会话）。
字段：`mode`（practice/exam/srs/paper/tuxing/deepbank）+ `origin`（pool/srs/paper:<id>）+
`started_at/ended_at/elapsed_ms` + `total/answered/correct/wrong` + `status`（active/submitted/abandoned）+ `meta`。

### 2.4 `import_batch` / `import_item`（补录管理，v9 新增）

v8 把批次与幂等台账塞在 `progress.importBatches` / `importedSigs` JSON 桶里，
「某本书补了多少、能不能撤销、这条为何被判重」只能翻 JSON。实体化后：
- 批次：`total/accepted/conflicts/rejected/imported_total/status/undone_at`；
- 条目：`sig/result/user_answer/correct_answer/is_correct/happened_at/canonical_id`。

**撤销语义**：软删（`status='undone'`）而非删除——「撤了什么」本身是可查事实。

### 2.5 `ingest_job`（题库管理作业归档，v9 新增）

v8 作业表只在内存 Map，宿主重启后「上次为什么失败」永久丢失（教训㊸）。
落库后跨进程可查：`action/key/url/state/elapsed_ms/error/log_tail/retried_from/created_dir`。
`created_dir` 是半成品清理判据（教训㊶：只删「本次新建 + 无 .git + 近乎空」的目录）。

### 2.6 `snapshot`（派生快照入表，v9 新增）

取代 `data/.paper-index.json` / `.huasheng13-index.json` 旁挂文件：
① 统一在库内（「只维护一个库」）；② 写路径可事务化；③ 带 `fixture_hash` 做失效判定。
**注意**：`huasheng13` 的**方法论正文**不是快照，而是 `knowledge` 表（可检索、可 JOIN）。

### 2.7 `knowledge` + `knowledge_fts`（知识层）

方法论/技能/考点都是**图节点**：`kn_id`（`hs13:<file>` / `skill:<file>` / `<kadian>`），
`kind` ∈ methodology/skill/kadian，`body` 截断 64KB（全文本体走引用，库只存检索所需）。
`knowledge_fts`（FTS5 trigram，外部内容表 `content='knowledge'`）让方法论检索**零外源直读**
——v8 是运行期扫 `references/*.md`。

### 2.8 `app_setting` / `migration` / `entity_attr`（控制面）

- `app_setting`：非引导配置的单一事实源（键词表由代码校验，值 JSON）。
- `migration`：迁移台账（`id/applied_at/ok/detail`），「这个库经过哪些迁移」可查——杜绝静默迁移。
- `entity_attr`：`(kind, ref, k)` 三元组，任意实体附加标注。与 `source_extras` 分工：
  `source_extras` = 上游原始对象（原样保真）；`entity_attr` = **本系统**新增标注（可过滤）。

## 3. 迁移纪律（每一条都来自一次事故）

| # | 纪律 | 事故 |
|---|---|---|
| M1 | 新列索引**不得**写进 `SCHEMA_SQL` | 旧库 exec 抛 `no such column` → 整库降级（v9 踩） |
| M2 | 新列一律 `ADD COLUMN` 追加在**末列**，不改既有列 | UPSERT 位置参数错位会静默丢列（cycle-40b/55） |
| M3 | 迁移必须**幂等**（PRAGMA 探测 + IF NOT EXISTS） | 重启即重复执行 |
| M4 | 迁移必须**留痕**（`migration` 表） | 「这个库怎么变成这样的」不可回答 |
| M5 | rebuild 只清 `POOL_TABLES`；用户态/控制面永不清 | 用户数据丢失（cycle-21 issue #2） |
| M6 | 镜像写入的列清单必须与 schema 同步 | 整本替换洗掉新列（v9 踩：`origin_batch` 消失） |
| M7 | FTS 外部内容表改动后必须显式 `rebuild` | 索引与内容失配（检索静默少结果） |

## 4. 可扩展性：三条「加东西」的固定路径

1. **加一个数据源** → `poolSourceImpls` 写 `ingestXxx` + `poolSources` 注册表加一条
   （主流程零改动，守卫 `SMOKE-KGDB-08`）。
2. **加一个有维度的管理域** → 建实体表（首列 ws）+ 在 `shared/storage.ts` 的
   `USER_TABLES` 登记 + `reviewStore`/域模块写存取函数。
3. **加一个无固定形状的域对象 / 实体标注** → `user_kv` 或 `entity_attr`，**零 DDL**。
4. **加一个缓存域** → `CACHE_DOMAINS` 登记策略 + `INVALIDATION_GRAPH` 登记依赖
   （守卫 `EVENT-05` 会强制覆盖性）。

## 5. 库体积与性能现状（2026-11-26 实测）

| 指标 | 值 |
|---|---|
| 库文件 | ~1.39 GB（含 question_source 230k + relation 570k + question_analysis 198k） |
| 题目 | 86,534（跨 7 源去重后） |
| 出处 | 230,083（一题多出处归集） |
| 关系 | 570,194 |
| 知识节点 | 9,721（kadian 9,685 + methodology 25 + skill 11） |
| 真题卷 | 0（本轮之前）→ 1683（按需摄入实测后） |
| FTS 检索 | 19–38ms |
| 全量 rebuild | ~4 分钟（事务内；无事务 421s → 事务 41s 是单源基线） |

**媒体纪律**：图片只登记 `rel_path + hash`，**不复制进库**（内容寻址已去重，
复制会让备份体积翻倍且丧失跨源去重）。故 `/api/*-img` 仍按路径取流——
那是媒体取流，不是题目事实直读，与 I-DB-1 不冲突。
