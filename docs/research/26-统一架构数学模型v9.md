# 26 · 统一架构的数学模型与数据结构（cycle-61 v9）

> 本文是 v9「统一架构收敛」的**数学总纲**：把六层能力（数据/检索/缓存/取题/错题补录/前端）
> 写成同一组代数结构的不同投影，并给出每条投影对应的落地代码位置与机器守卫。
> 纪律（沿用研究 25）：**只写有落地的**——每条结论都能指到文件与函数，空谈不入本文。

---

## 1. 为什么需要「同一个模型」

v8 及以前的问题是**同一个概念在多处被独立建模**：

| 概念 | v8 的不同模型 | 后果 |
|---|---|---|
| 「数据在哪」 | 每域自己判断（fresh? paperRows>0? 目录存在?） | 六域六套门，一个域漏判就回落外源 |
| 「检索结果」 | 五种形状（results/list/count/total/hits） | 消费方按源分支，新源必漏 |
| 「缓存键」 | 七处各自拼字符串 | 漏 ws 维度 → 跨项目污染（R20） |
| 「抽题配额」 | 两处手写 `Math.min` | 改一层规则漏另一处（MAT-02） |
| 「错题真相」 | JSON 数组 + 库影子 | 影子滞后，谁是权威不可判定 |
| 「视图」 | 导航数组 + 路由表 + manifest 三份 | 幽灵视图 / 同名异键 |

v9 的统一不是「把代码搬到一个文件」，而是**给每个概念一个唯一的数学对象**，所有层都从它派生。

## 2. 六个代数结构

### 2.1 数据域 = 五元组（唯一的「数据在哪」模型）

```
Domain D = ( id, S_D, T_D, R_D, mode )
  S_D  ⊆ Sources        该域的数据由哪些摄入源提供（poolSources 注册表 id）
  T_D  ⊆ Tables         该域数据在库内的落点（表 + 谓词）
  R_D  = ⋀_{t∈T_D} count(t) ≥ min(t)     就绪谓词（可机器判定）
  mode ∈ {sync, background}               就绪失败时的等待策略
```

**落地**：`src/shared/domains.ts`（`DOMAINS` 六域 + `domainReady` 派生）；`src/server/dataGate.ts`（`ensureDomain`）。

**不变量 I-DB-1**：运行期读路径不含源文件 IO。
形式化：`∀ request r, domain d = D(r) ⇒ readPath(r) ⊆ T_d(DB)`，且源文件只在 `adapter.ingest` 出现。
**机器守卫**：`C60-FRESH-03/04`（源码去注释后断言无 `buildPaperIndex`/`naokuReady`）+ `SMOKE-DOMAIN-*`。

**为什么 `mode` 是域属性而不是全局配置**：实测 gwy-zhenti 首次摄入 149s、naoku 数十秒，
而 question/tuxing/method 都在 1s 量级。把等待策略做成**域的固有属性**，才能让
「轻域同步、重域后台」成为声明而不是散落的 if。

### 2.2 检索 = 信封（唯一的「结果长什么样」模型）

```
Hit      = ( id, source, title, snippet, score?, meta?, provider )
Envelope = ( query, results: Hit[], total, took?, confidence? )
Provider = ( id, endpoint, domain, search: (q, opts) → Envelope )

Aggregate(ids, q) = roundRobin( { Envelope_p | p ∈ ids } )      // 保留各组原序
```

**关键决策**：**不合并打分**。五源打分语义不同（FTS5 bm25 / BM25 字段加权 /
无打分子串 / SQL LIKE 聚合 / 三通道串联），跨源比较分数是无定义的。
故聚合只做「交替合并 + 分组保留」，每条 hit 带 `provider` 可归因。

**落地**：`src/server/searchRegistry.ts`（`search` / `searchMany` / `list`）；
`/api/search/unified`（`providers=a,b,c`）。

**不变量 I-SEARCH-1**：单查与聚合同形（都带 `provider`）。
理由：消费方只写一套渲染。**反例（本轮真实缺陷）**：v8 单查不带 `provider`，
守卫 `C61-RT-01` 立刻假红——「同一数据两条路形状不同」正是漂移的起点。

**不变量 I-SEARCH-2**：空结果不缓存。
形式化：`total = 0 ⇒ ¬cache.set(key)`。理由：空有两种成因（真无命中 / 数据未入库），
缓存第二种会让「装好题库后 30s 仍搜不到」。**守卫**：`C61-RT-04`。

---

### 2.3 缓存 = 键空间 + 失效图（唯一的「什么时候该重算」模型）

```
Key      = domain | ws | root | stableParams(params)        // 四维显式
Snapshot = ( domain, fixtureKey, value )                    // 昂贵计算物化（无 TTL）
Graph    = domain → [派生域]                                 // 失效图（偏序）

invalidateDomain(d) = { k | k.domain ∈ {d} ∪ Graph*(d) }    // 传递闭包
emitDataChanged(entity) = invalidateDomain(entity) ∪ 通知订阅者
```

**为什么快照与 TTL 缓存要分开**：材料组索引（全表扫 507ms）的真相由**数据写入事件**
定义，不由时间定义。给它 TTL 只会「过一会儿重新扫一遍」；给它事件才能「写完立刻失效」。

**不变量 I-CACHE-1**：失效图必须覆盖所有有策略的派生域。
形式化：`∀ d ∈ CACHE_DOMAINS, d ∈ sources ∨ ∃ s ∈ sources: d ∈ Graph(s)`。
**这条不变量在本轮抓到两个真实缺口**（`paperIndex` 与 `tuxing` 无人清）——
说明它不是形式主义，而是**能抓到 bug 的判据**。**守卫**：`EVENT-05`。
落地：`src/server/cache.ts`（`CACHE_DOMAINS` / `INVALIDATION_GRAPH` / `snapshot` / `stats`）。

**不变量 I-CACHE-2**：写入路径不各自手写失效，只调 `emitDataChanged`。
理由：模型只有一处（`src/server/dataEvents.ts`），新增缓存域只改失效图，不改写入点。

### 2.4 取题 = 配额函数 + 加权抽样（唯一的「抽多少、抽哪些」模型）

```
plan(n, layers) = fold( layers, (left, cap) → min(cap, left) )     // 守恒 + 让渡
                性质：Σ plan ≤ n,  plan_i ≥ 0
pick(w, k)      = 无放回加权抽样（权重正比 → 越弱越密）
weights         = weaknessWeight(rate) = 1 / (rate + 0.15)
moduleWeights   = [ weaknessWeight(rate_m) ]，无数据时 rate = prior（**调用方声明**）
```

**两条性质为什么必须显式**：
1. **守恒**：Σ 配额 ≤ n。旧代码逐层 `Math.min` 手写，`count=1` 时曾返回 2 题（容量闸缺失）。
2. **让渡**：高优先层占满即无剩余。旧代码 L0 材料组曾占满全配额 → 五维层零名额（MAT-02）。

**先验为什么是参数而不是常量**：`rate` 无数据时，SRS 抽题用 0.5（中性，不偏爱新模块）、
排程与池抽题用 0（新模块优先）。这是**业务语义差异**，藏进内核默认值就再也看不见了
（cycle-50 纪律）。

**落地**：`src/shared/kernel.ts`（`quotaPlan` / `weightedPickIndex` / `moduleWeakness`）；
`poolApi.sampleQuestions`（四层配额）、`srs.srsQuestions`（模块选择）均已改为调用它。
**守卫**：`QUOTA-01..03`、`PICK-01..05`、`WEAK-01..02`、`C61-TAKE-02`（配额计划随响应透出）。

---

### 2.5 错题/补录 = 权威库 + 镜像（唯一的「谁是真相」模型）

```
Authoritative(t) = DB(t)                     // 库是权威读源
Mirror(t)        = JSON(t)                   // JSON 是兼容写回（旧消费方/统计口径）

read(t)  = if |DB(t)| > 0 then DB(t) with tier='db'
           else if JSON(t) 非空 then JSON(t) with tier='json'
           else ∅ with tier='none'
write(t) = upsert(DB(t)) then writeJSON(t)   // 顺序：先库后镜像
```

**为什么必须反转权威方向**：v8 是「JSON 权威 + 库影子」，于是白盒看到的库行数永远滞后，
且 `wrong_book` 的增强字段（canonicalId/kadian/lapses）无处落地——因为影子只跟随 JSON 的字段集。

**单条 upsert 而非整本替换**：SRS 的真相是「每题一行」，整本替换在并发下后写覆盖先写。
**本轮真实缺陷**：`mirrorProgressToDb` 的 INSERT 列清单没跟上 v9 新列 →
整本替换把 `origin_batch`/`historical` 洗成 NULL → 补录来源消失。**与 cycle-43
「整本替换会丢字段」是同一条纪律的第 N 次验证。**

**不变量 I-REVIEW-1**：移除/撤销必须双侧同步。
形式化：`removed(s) ⇒ ¬read(s)`。**守卫**：`C61-REV-02`（移除后不得再出现）、
`C61-REV-03`（撤销后错题同步消失）。
落地：`src/server/reviewStore.ts`（`readWrongBook` / `upsertWrongEntry` / `wrongDiagnostics`）。

### 2.6 前端视图 = 元数据注册表（唯一的「有哪些页面」模型）

```
ViewMeta = ( id, label, icon, group, order, domain, desc, viaHub? )
Nav      = groupNav( ViewMeta 按 group·order 排序 )            // 导航派生
Routes   = { id → Component }（组件是运行时引用，与元数据分离）
```

**不变量 I-VIEW-1**：`ids(Routes) ≡ ids(ViewMeta)`（双向）。
理由：只有元数据 = 点了空白；只有路由 = 不可达/白盒看不见。
**守卫**：`C61-VIEW-02`（双向对账）。
落地：`src/client/view-registry.ts`（`VIEW_META` / `buildNavGroups` / `auditViewMeta`）。

**页面融合判据（v9 结论）**：一个页面该不该独立存在，看它是否承载**独立数据面**。
- `search`（知识正文检索） vs `pool`（题目检索）：不同数据面 → 都保留。
- `method`（kaogong-skill 十主题） vs 专题·方法论（花生十三六模块）：同一数据面 → method 降为子页。
- 枢纽内视图（practice/tuxing/deepbank/essay/huasheng13）不占一级导航（纪律㉛）。

## 3. 六层之间的依赖方向（单向，不得回环）

```
        ┌──────────────────────────────────────────────┐
   L5   │ 前端（view-registry → 导航/路由；视图自治取数） │
        └───────────────────┬──────────────────────────┘
                            │ 只经 HTTP 端点（同源 /kaogong/*）
        ┌───────────────────▼──────────────────────────┐
   L4   │ 服务域（data/paper/naoku/tuxing/method/...）   │
        │  · 读路径只经 dataGate + pool 读层              │
        └───────────────────┬──────────────────────────┘
                            │ domainReady / ensureDomain
        ┌───────────────────▼──────────────────────────┐
   L3   │ 统一机制层                                      │
        │  cache（键+失效图）· searchRegistry · reviewStore │
        └───────────────────┬──────────────────────────┘
                            │
        ┌───────────────────▼──────────────────────────┐
   L2   │ 存储层 .kaogong.db（schema v9 / 26 表）          │
        └───────────────────┬──────────────────────────┘
                            │ 只在摄入期
        ┌───────────────────▼──────────────────────────┐
   L1   │ 适配层（poolSources 注册表 + 各源 ingest）       │
        └───────────────────┬──────────────────────────┘
                            │ 只读
        ┌───────────────────▼──────────────────────────┐
   L0   │ 外源（16 仓库，只读，永不修改）                  │
        └──────────────────────────────────────────────┘
```

**分层纪律（可机器判定）**：
- L1 不得 import L3/L4（适配层不认识缓存与服务）——本轮把「数据变更广播」做成
  **注入钩子** `opts.onDataChanged`，而不是让 `poolIngest` import `dataEvents`。
- L4 不得直读 L0（I-DB-1）。
- L5 不得读 fs（I4，`SMOKE-KERNEL-01`）。

## 4. 本轮由模型直接推导出的缺陷清单（不是先写代码后补文档）

| # | 模型违反 | 症状 | 修复 | 守卫 |
|---|---|---|---|---|
| 1 | I-DB-1 存在六条回落分支 | 池未就绪时静默读外源，功能时好时坏 | 删除全部回落，改 dataGate 按需摄入 | C60-FRESH-03/04 |
| 2 | schema 新列索引写进建表脚本 | 旧库 exec 抛 `no such column` → 整库降级（pool ready=false） | 索引移入迁移函数 | C60-06 |
| 3 | I-CACHE-1 失效图不全 | `paperIndex`/`tuxing` 改数据后仍读旧值 | 补失效图 | EVENT-05 |
| 4 | I-SEARCH-1 单查缺 provider | 聚合/单查两种形状 | 单查补标注 | C61-RT-01 |
| 5 | I-SEARCH-2 空结果被缓存 | 装好题库后仍搜不到 | 只缓存非空 | C61-RT-04 |
| 6 | ctx 句柄键名漂移（`pool` vs `poolApi`） | pool provider 恒空但直连正常 | 显式 `poolOf()` + 响亮失败 | C61-RT-01 |
| 7 | 配额手写且不守恒 | count=1 可能返回 2 题 | quotaPlan | QUOTA-01 |
| 8 | I-REVIEW-1 单侧删除 | 移除错题后又出现 | 双侧同步 | C61-REV-02 |
| 9 | 镜像列清单落后于 schema | 补录来源（origin_batch）被洗掉 | 补齐列清单 | C61-REV-03 |
| 10 | I-VIEW-1 三处导航漂移 | 幽灵视图/点空白 | 视图注册表 | C61-VIEW-02 |

**这张表是本轮的方法论证据**：先有模型与不变量，再由不变量去**找**违反，
而不是「先改代码，事后写文档总结」。10 条里有 6 条是我写完模型后被守卫/实测抓出来的。

## 5. 性能口径（由模型决定策略，而非拍脑袋）

| 位置 | 模型角色 | 实测 | 策略 |
|---|---|---|---|
| `question` 四层配额 | 配额函数 | 稳态 ~88ms | 层内随机、层间确定性（守恒才可断言） |
| FTS5 trigram 检索 | 信封源 | 19–38ms | 候选上限 500 + bm25 排序 |
| 快照（材料组索引） | Snapshot | 首建 507ms → 请求 0.09ms | 事件失效，无 TTL |
| 检索信封缓存 | Key-TTL | 命中 <1ms | 30s TTL + 空结果不缓存 |
| 重量级域摄入 | Domain.mode=background | gwy-zhenti 149s | 后台 + single-flight + 60s 冷却 |
| 按域轻量摄入 | Domain.mode=sync | <1s | 请求内完成，用户无感 |

**纪律**：稳态 <100ms 的端点不再加缓存层（cycle-45 过度工程收口）。
