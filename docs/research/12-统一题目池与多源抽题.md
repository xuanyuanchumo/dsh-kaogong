## 1. 数学与模型定义

### 1.1 问题形式化

当前练习链路是**单源映射**：

```
抽题 : (module, count) → xingcezhenti 中随机一份试卷的前 30 题中随机取 count 题
```

目标状态是**多源偏序采样**：

```
抽题 : (module, kadian?, source?, count, policy) → 统一题目池中按策略取 count 题
统一题目池 : (canonical_id, 题干, 选项, 答案, 解析, 图, 五维标注, 出处集合)
```

### 1.2 跨源题目身份：三层判据

要把多个源的题目放进同一个池子，必须先回答「这两条记录是不是同一道题」。定义判据优先级：

```
identity(q) =
  L1  上游内嵌 qid        （最强：跨仓库共享同一 ID 体系）
  L2  内容指纹 fp = sha1(normalize(stem+options+answer))
  L3  归一化内容哈希 h = sha256(normalize(stem+options+answer))[0:16]

normalize(s) = 去 HTML 标签 → 全角转半角 → 去标点空白 → 统一小写
```

去重安全性的经验判据：若 **同一 fp 对应多个 qid** 的比例极低，则 fp 可作合并键；反之必须回退到 L1/L3。

### 1.3 抽样策略：分层加权

当前算法「随机文件 + 前 30 题 + 随机下标」的**有效样本量**被三重压缩：

```
可达题集 = ⋃_{f ∈ files} 前30题(f)     ⇒  |可达| ≪ |全集|
分布偏斜 = P(题) ∝ (该题所在试卷被抽中的概率) × (该题在前30题内的位次)
```

改进为**分层加权采样**（按考点 kadian 分层）：

```
P(q) ∝ w(kadian(q)) · w_weak(module(q)) · w_srs(state(q))
其中 w_weak = 1/(rate+0.15)（复用 SRS 同源模型，单一事实源纪律）
     w_srs  = 未掌握错题最久先回炉（FIFO 贪心）
```

### 1.4 数据库载体选择

设目标库 B 有两个候选：(a) 扩展现有 `.naoku.db`；(b) 新建独立库 `.unified.db`。判据是**重建语义**：

```
若 B 的生成方式 = f(上游) 且 f 是全量重写 ⇒ B 不可承载项目自有表（写入即被冲掉）
若 B 可增量追加 ⇒ 可承载
```

## 2. 本插件代码落地（含实测证据）

### 2.1 缺陷定位：练习链路硬锁单源

| 落点 | 事实 |
|---|---|
| `src/adapters/repoData.ts` `getRandomQuestions` | `join(repoRoot, 'xingcezhenti', dirName)` —— **仓库名硬编码** |
| `src/server/http.ts` `/api/questions` | 参数仅 `module`/`count`/`sort` —— **无来源参数** |
| 同上 | `randomFile` 随机选文件 → `parseQuestions(..., 30)` **只解析前 30 题** → 再随机取 count 题 |
| `src/server/naokuApi.ts` | `/api/naoku/questions` 锁 GongkaoNaoku |
| `src/server/tuxingApi.ts` | `/api/tuxing/list` 锁 gk-tuxing |
| `src/server/paperApi.ts` | `/api/papers/*` 锁 gwy-zhenti |

**三个叠加后果**：

1. **可达集被压缩**：每次抽题只来自一份随机试卷的前 30 题，模块内考点轮换极慢。
2. **与已装源脱钩**：只装「深度题库 + 图推」而不装 xingcezhenti 的用户，专题刷题**直接不可用**（C33 教训同族：功能存在 ≠ 功能可用）。
3. **五维标注未贯通**：GongkaoNaoku 的 `reasoning`/`fastest`/`pitfalls`/`mother`（信息密度最高的资产）只在深度库视图可用，练习链路完全不消费。

### 2.3 实测：`.naoku.db` 的重建语义（决定载体选择）

`src/adapters/naoku.ts` 合并逻辑实测：

```ts
if (existsSync(target)) { dbPath = target; return target }   // 存在即复用
parts = readdirSync(srcDir).filter(f => /^kaogong\.db\.part-\d+$/.test(f)).sort()
writeFileSync(target, Buffer.concat(bufs))                    // ← 整库拼接重建
```

⇒ **`.naoku.db` 是上游分片的整体拼接产物**：上游更新 → 本地库被**整体重写**。
**因此：往 `.naoku.db` 写项目自有表会被静默冲掉** —— 这是选型的决定性依据。

### 2.4 实测：载体能力基线

| 能力 | 实测 |
|---|---|
| FTS5 外部内容表（`content='q'`） | ✅ 可用（`位置规律`/`同比增长` 均命中） |
| ATTACH 多库 | ✅ 可用 |
| `.naoku.db` 可写 | ✅（`query_only=0`，journal_mode=delete） |
| 批量插入吞吐 | **12.3 ms/千题**（10 万行 1.23 s） |
| 解析吞吐（瓶颈） | **0.56 ms/题** ⇒ 100 万题 ≈ 9.3 min |

⇒ **插入不是瓶颈，解析才是**（快 45 倍）。优化重点应放在解析与增量策略，而非写入。

### 2.5 各源题目形态差异（统一模型的难点）

| 源 | 题干 | 选项 | 图 | 解析 | 特有字段 |
|---|---|---|---|---|---|
| xingcezhenti | ✅ 纯文本 | ✅ A-D 对象 | ✅ `kgimg://` 占位 | ✅ | `groupMaterial`/`groupMaterialNo`（材料组） |
| GongkaoNaoku | ✅ HTML | ✅ JSON | ✅ `img_refs`（.webp 名 vs .png 磁盘） | ✅ | **五维标注** kadian/reasoning/fastest/pitfalls/mother |
| gwy-zhenti | ✅ 纯文本 | ✅ | ✅ 段落大图/题图 | ✅ `<details>` 内 | `material`/`groupMaterial` |
| gk-tuxing | ❌ **纯图无文字** | ✅ 含在整图 | ✅ `assets/q/g{n}_{nn}.png` | ✅ exp/acc/trap | **13 类规律标签** `CAT_NAMES` |

**统一模型必须容纳的差异**：

1. **gk-tuxing 无题干文字** —— 卡片形态是「整图 + 规律标签 + 解析」，与文字题的「题干 + 选项」不同构；
2. **材料组**（资料分析/篇章）—— 题目依赖共享材料，必须保持 `groupMaterial` 绑定；
3. **图片路径协议** —— `kgimg://`（xingcezhenti）与 `img_refs`（naoku）两套引用，须在统一模型层归一为 `{source, relPath, hash}`；
4. **五维标注** —— 是 naoku 独有，但**不应**成为字段必填（其它源为空）。

## 3. 中文思维：学习场景启发

- **「散珠须穿成串」**：考公题库是散珠——真题卷、深度库、图推专项，各有所长。串珠的线就是**题目身份**。幸而上游已给了线（共享 qid），我们只需穿，而不是打结另造一套。
- **「取书先立目」**：读书人取书不随手翻，而先按目录、按篇目找——「随机抽一份卷的前 30 题」相当于**随手翻书**。分层采样就是**先立目，再取篇**。
- **「同一题在不同卷出现，正是它的价值」**：1204 道题跨卷复用、3 例指纹冲突极低 —— 说明题库之间本就有共识。统一池把「共识」显性化：**一题一处作答，多处溯源**。
- **「库可并存，池须唯一」**：多个题库像多个藏书楼，可并存；但**取书处**必须唯一，否则读者永远不知道该去哪本书找。统一题目池就是那个唯一的取书处。
- **「重建之库不可藏私货」**：`.naoku.db` 是上游的投影，上游一变它便整库重写——**在别人的库上盖自己的房子，迟早被拆**。自有数据须自有载体，这是常识，也是本轮最硬的工程约束。

## 4. 工程实践价值

1. **「新建库」是必要但不充分**：新库是**载体**，不是**方案**。真正要解决的三件事是：① 统一题目模型（字段差异见 §2.5）；② 跨源身份映射（qid 已有 ✅）；③ 抽样策略（分层加权）。只建库不改抽样，抽题质量依旧是「随机文件前 30 题」。
2. **载体选择：新建独立库 `.unified.db`，不往 `.naoku.db` 写**：后者是上游投影（§2.3），整体重建会静默冲掉自有表；且上游合并库只服务 naoku 一源，把全源数据塞进去会混淆「谁的产物」。**新库边界清晰**：上游投影留在上游库，项目自有派生物落在自有库，两者以 `qid` 关联。**
3. **qid 是上游间的事实标准，不是本项目的发明**：327/327 的跨仓匹配率证明两仓已用同一 ID 体系。dsh-kaogong 的职责是**消费并扩展**（补 gk-tuxing/gwy-zhenti 的映射），而非另造 canonical_id —— 上一轮设计文档里提出的 `'h:' || sha256(...)` 兜底方案应降级为**最后手段**。
4. **fp 去重几乎零风险**：仅 3 例同 fp 多 qid（28669 fp / 27506 题）。这是「同题多源聚合」得以安全实施的关键前提，也是 P0 阶段最该先验证的指标。
5. **解析是瓶颈不是写入**：插入 12.3ms/千题 vs 解析 0.56ms/题，差 45 倍 ⇒ 优化方向是**增量解析**（按 hash+mtime 只扫变更）与**解析复用**（同一 md 不重复解），不是数据库调优。
6. **抽样策略复用 SRS 同源模型**：`w_weak = 1/(rate+0.15)` 已是全仓单一事实源（C30b 纪律：同一业务语义全仓只有一个公式），统一抽题**不得**另写一套权重公式。
7. **五维标注贯通是最高性价比收益**：naoku 的 `reasoning`/`fastest`/`pitfalls`/`mother` 已在库中，练习卡片消费它**零额外存储成本**，直接把「为什么这么想」送到用户眼前。

**新增守卫（随实施落地）**：

- `SMOKE-POOL-01`：统一池条目数 = 各源去重后条目数之和（增量幂等）
- `SMOKE-POOL-02`：跨源同一 qid 在池中**只有 1 条**，且 `appearances` 列出全部出处
- `SMOKE-POOL-03`：抽题接口支持 `source` 参数（`xingcezhenti`/`naoku`/`tuxing`/`papers`/`all`）
- `SMOKE-POOL-04`：**抽题分布不再偏斜** —— 同一模块连续抽 N 次，覆盖的考点数 ≥ 阈值（回归守卫，防「随机文件前30题」复活）
- `SMOKE-POOL-05`：上游仓库 `git status` 干净（只读约束）
- `SMOKE-POOL-06`：`.naoku.db` 重建后统一池不受影响（载体隔离守卫）
