### 2.2 发现一个真实设计缺口：**canonical_id 的 id 空间冲突**

**问题**：`deriveCanonicalId` 无条件 `q:<qid>`。粉笔系（naoku/xingcezhenti/kaogongzhentizhengliu）的 qid
是**共享命名空间**（跨仓 327/327 一致——这正是研究 12/13 的合并键）；但 xingce-app（id=44152）、
qiuzhao（id=1001）、civil-exam-agent（id=Q_01）是**独立 id 空间**。

当前不撞是**巧合**（粉笔 qid 8 位、xingce-app id 5 位），不是设计。未来任何源接入都可能撞库——
两个不同上游的题合并成一个 canonical_id = **跨源身份污染**（比漏摄入严重得多）。

**修正（最小且向后兼容）**：

```
canonical_id 派生规则（v2）：
  ① 源声明 qidNamespace（注册表 SourceSpec 新字段）
     · 共享同一 namespace 的源 → 'q:' + qid          （跨源自动合并，粉笔系）
     · 独立 namespace 的源     → 'q:' + sourceId + ':' + qid（源内唯一，永不撞库）
  ② 无 qid 有 fp → 'fp:' + fp
  ③ 都没有       → 'h:' + sha256(stem) 前 16
```

- 已入库数据（naoku/xingcezhenti = 粉笔系）canonical_id **不变**（向后兼容）。
- 新源（xingce-app 等）从 `q:xingce-app:44152` 形态起步。
- 跨源等价关系（若未来发现 xingce-app 题与粉笔题同题）走 **SAME_AS 边**（带 evidence）——
  这本就是研究 13 §1.3 的合并机制：**合并靠关系边，不靠 id 撞库**。

**守卫**：`SMOKE-KGDB-10`（独立命名空间源的 canonical_id 必含源前缀；共享命名空间源不带）。

## 4. 中文思维

- **「户口与租客」**：canonical_id 是**户口**——粉笔系三仓本是一家人（同一个 qid 户口本），
  外来租客（xingce-app/qiuzhao）不能冒用别人户口号，要落**自己的户口**（源前缀）。
  之前不撞是运气，运气不是设计。
- **「合并靠认亲，不靠重名」**：两个张三不一定是同一人。跨源等价（SAME_AS）要**带证据认亲**
  （qid 命中 / fp 命中 / 人工校验），而不是「名字一样就算同题」。
- **「先清点后进货」**：16 仓库不是 16 个都装题。先逐仓开箱验货（本轮审计），再决定哪些上架——
  否则 schema 会为不存在的数据空转，摄入器会为空目录写一堆 if。
