## 1. 数学与模型定义

### 1.1 统一身份：内容指纹与规范题目 ID

多源题库的「同一道题」判定是**集合归并**问题。定义题目规范身份：

```
canonical_id(source, item) =
    'q:' || qid                                   若源提供稳定题目 ID（naoku 系）
  | 'fp:' || sha1(normalize(stem+options+answer)) 若源提供内容指纹（appearances.fp）
  | 'h:'  || sha256(normalize(stem+options+answer))[0:16]   兜底（无 ID 无指纹）

normalize(s) = 去除 HTML 标签 → 全角转半角 → 去标点空白 → 统一小写
```

跨源去重归结为**等价类合并**：以指纹 `fp` 为键分组，同组题目合并为一条 canonical 记录，保留 N 处出处（paper/region/year/seq）。

### 1.2 统一检索：FTS5 trigram 与 BM25 的取舍

零 npm 运行时依赖约束下，中文全文检索只有两条路：

| 方案 | 匹配单位 | 中文表现 | 依赖 |
|---|---|---|---|
| BM25 + bigram（现有 `huasheng13.ts`） | 2-gram | 可用，但**分词边界漂移** | 自实现，零依赖 ✅ |
| **FTS5 trigram**（SQLite 内建） | 3-gram | ✅ 实测全命中 | SQLite 内建，零依赖 ✅ |

trigram 的性质：对长度 ≥3 的中文串做**子串匹配**，无需词典分词；短于 3 字的查询（如「数量」）需降级为 LIKE 或 bigram 兜底。

召回质量用 BM25 口径衡量：

```
score(q, D) = Σ IDF(t) · (tf(t,D)·(k1+1)) / (tf(t,D) + k1·(1-b + b·|D|/avgdl))
              k1 = 1.2, b = 0.75
```

**已验证的坑（cycle-18 教训㊜）**：中文 bigram 下任何中文串都会产生命中，**噪声分数反而高于真实短查询**（「数量」1.68 vs「不存在的词」4.79）→ 阈值过滤会误杀真实查询。正解 = **只裁尾**（`score < max(1.0, top×0.15)` 且**永留首条**）+ 三档 `confidence`/`phraseHit` 提示，**低置信度结果不丢弃**。该纪律同样适用于 FTS5 统一索引层。

### 1.3 摄入成本模型

设全库题目数 N、解析吞吐 r（题/毫秒）、检索延迟 L：

```
T_ingest = N / r          一次性/增量重建耗时
T_query  = L + log(N)     B-tree/FTS 倒排查找
```

实测 `r = 1/0.56 ≈ 1.79 题/ms`，N ≈ 100 万（16 源去重前）⇒ T_ingest ≈ 9.3 分钟（一次性，可接受）；增量按 hash+mtime 只扫变更文件，秒级。

### 1.4 图推的可检索特征：模板化题干的信息论视角

图推题干的**互信息极低**：真题卷 135 道图推题的题干几乎都是同一句「从所给的四个选项中，选择最合适的一个填入问号处，使之呈现一定的规律性：」，**单独用题干检索的区分度≈0**。

但**解析文本**的区分度极高：

> 「元素组成基本相同，优先考虑位置规律。题干图形出现十六宫格，黑色三角形均存在三个顶点，其中外圈的两个顶点在外圈依次逆时针平移一格」
> 「元素组成相同，但无明显位置规律和属性规律，考虑数量规律。题干图形面数量依次为0、1、2、3」

⇒ **图推的可检索特征 = 解析文本中的「规律类型 + 特征描述」**，而规律类型恰好是 gk-tuxing 已有的 13 类离散标签：

```
空间重构 · 位置 · 面数量 · 对称性 · 样式 · 笔画数 · 线条规律
元素种类 · 点规律 · 曲直性 · 角数量 · 特殊规律 · 综合规律
```

这把图推从「图像检索问题」降级为「文本检索问题」，从而**复用现有 FTS 层，无需图像 embedding**。

### 1.5 模型自选：provider/model 路由契约

宿主 DSH 的模型选择是一个**二元组**：

```
(provider: string, model: string, reasoningEffort?: string)
```

助手消息记录产生它的提供方与模型（`AssistantProviderMetadata.provider/model`），模型选择有持久化事件 `event:model/selection`。插件若需自选模型，须使用宿主已配置的路由（`ctx.llm`），而非自带 key —— 否则产生第二套凭据体系。

## 3. 中文思维：学习场景启发

- **「众库一册」是备考的基本功**：考公题库天然分散——真题卷、深度题库、图推专项、方法论笔记各有出处，如同「五经异本」。考生真正的问题不是「缺哪本书」，而是**「这一道题我到底在哪本书上见过」**。统一索引解决的不是存储问题，而是**溯源与去重**问题：同题多本，不应重复刷、重复记、重复怕。
- **「题在多本，答案在一处」**：错题本的真正价值在于**同一道题的多处出处能汇到一处**——如同《四书章句集注》把历代注疏并置，考生一眼看到某题在国考 2021、在省考 2019、在深度库里都有，且答案一致。`appearances` 表的 58890 条正是这个「汇注」结构。
- **「题干是壳，解析是肉」**：图推题的题干千篇一律，恰似科举八股——题目形式固定（破题承题），**真正区分题目的是「破题」的展开**（解析里的规律与特征）。所以搜图推要搜解析，不是搜题干。这个直觉与「以题面索骥，不如以注解求证」同理。
- **「图片是入门的路，不是索引的钥匙」**：古人抄书只抄文字不抄图版，是因为图版难传难校；今天图片唾手可得，反而容易把「看图」误当「可检索」。真正让图可检索的，是把图**还原成文字描述**（规律+特征），而不是让机器去比对像素。
- **「选模型如选刻本」**：同一份材料，用不同的刻本（模型）校读，得出的精粗不同。宿主提供模型路由，插件应让用户**自选刻本**，而不是替用户钉死一家——这也符合本插件「只做整合层、不自建体系」的既有立场。

## 4. 工程实践价值

1. **统一身份层已被验证，且是现成资产**：`.naoku.db` 的 `qid` + `appearances` 已实现 100% join 的跨源映射。统一存储方案**不需要推倒重建**——是把既有能力从「naoku 单源」推广到「全源」，边际成本远低于新建体系。这是本次评估最重要的修正。
2. **FTS5 trigram 是零依赖约束下的最优解**：实测中文全命中、检索 <1ms、摄入 0.56ms/题，且**不引入任何 npm 运行时依赖**（项目硬约束）。对比 BM25+bigram 自实现：FTS5 省掉倒排表自维护与分词漂移，代价是短查询（<3 字）需降级。
3. **分层存储避免 L3 的成本倒挂**：216266 张图已是内容寻址（sha256 文件名），复制进 SQLite 会**丧失跨源去重能力**且使备份体积翻倍。正确做法是 L1 登记 `rel_path + content_hash` 做引用，媒体留在上游目录。
4. **PDF 源分层处置**：1403 个 PDF / 1929.7MB，**独有 2000–2007 早期真题**（md 源从 2008 起）且含独立「答案及解析」版；而 2008–2022 段与 md 源同题。OCR 全量成本极高（估 10+ 小时 CPU）而边际价值低 ⇒ **先 L1 登记、后按需解析**。同理，图推选项图的正解是 gk-tuxing 现有 354 张整图，**不值得为 PDF 另建渲染管线**。
5. **模型自选须走宿主路由**：`ctx.llm` + `ImageAttachmentAccess.readonlyPath` + `ctx.attachments`（内容寻址持久化到 `<DSH_HOME>/attachments/v1`）构成完整的多模态调用链。插件自建 key 会产生第二套凭据体系，与「整合层不重复造轮子」的定位冲突。
6. **结构化抽取必须直连模型**：现有 `kaogong_ai_*` 是「素材供模型加工」，适合长文本点评；但图片识别需要**schema 约束的结构化输出**（规律类型/特征描述），agent 侧通用处理无法保证结构 ⇒ 需要 `ctx.llm` 直连这一条新路径，与现有工具并存而非替代。

## 5. 验证方式（可运行）

```bash
# ① 统一身份层现状（.naoku.db 的 qid/appearances 统计）
cd dsh-kaogong && node -e "
const {DatabaseSync}=require('node:sqlite');
const db=new DatabaseSync('data/.naoku.db',{readOnly:true});
console.log(db.prepare('SELECT COUNT(*) q, COUNT(DISTINCT qid) dq FROM questions').get());
console.log(db.prepare('SELECT COUNT(*) a, COUNT(DISTINCT fp) df FROM appearances').get());
console.log(db.prepare('SELECT COUNT(*) c FROM (SELECT qid FROM appearances GROUP BY qid HAVING COUNT(DISTINCT fp)>1)').get());
"

# ② FTS5 中文 trigram 可用性
node -e "
const {DatabaseSync}=require('node:sqlite');
const t=new DatabaseSync(':memory:');
t.exec("CREATE VIRTUAL TABLE f USING fts5(q, tokenize='trigram')");
t.exec("INSERT INTO f(q) VALUES('元素组成基本相同，优先考虑位置规律')");
console.log(t.prepare('SELECT COUNT(*) c FROM f WHERE f MATCH ?').get('位置规律'));
"

# ③ 既有门禁（改动后必跑）
cd dsh-kaogong && npm run build && npm run test:all
```

**新增守卫（随 S1/S2 落地）**：

- `SMOKE-UNIFIED-01`：统一索引条目数与 L1 资产账本一致（增量幂等）
- `SMOKE-UNIFIED-02`：跨源检索一次命中 ≥3 个源
- `SMOKE-UNIFIED-03`：同题多源聚合去重为 1 条且列出 N 处出处
- `SMOKE-UNIFIED-04`：中文 trigram 检索命中（位置规律/十六宫格/三视图）
- `SMOKE-UNIFIED-05`：上游仓库 `git status` 干净（只读约束守卫）
