# 17 · 性能研究：`.kaogong.db` 白盒面板的量化归因与优化

> dsh-kaogong 研究文档 · cycle-36 · 目标驱动（性能研究 → 落地 → 闭环）
> 前置：[16-题库覆盖审计.md](./16-题库覆盖审计.md)（池 51211 题 / 346797 边 / 141489 出处）

## 1. 现状实测（2026-11-19 live host · 58020）

### 1.1 遥测慢端点排行（p95）

| 端点 | p95 | 阈值 | 判定 |
|---|---|---|---|
| `/api/pool/rebuild` | 220850ms | 500 | ℹ️ 全量重建本身是长任务（5.4 分钟，预期行为，不优化——**应改为异步作业**见 §5） |
| `/api/pool/status` | **1006ms** | 500 | ❌ error |
| `/api/pool/health` | **788ms** | 500 | ❌ error |
| `/api/pool/questions` | **766ms** | 500 | ❌ error |
| `/api/pool/search` | 361ms | 200 | ⚠️ warn（FTS 本体 13.5ms——开销在别处） |
| `/api/pool/relations` | 321ms | 200 | ⚠️ warn |
| 其余 67 端点 | ≤62ms | — | ✅ 全部健康 |

### 1.2 逐查询归因（SQLite 直测，51211 题）

| 查询 | 耗时 | 调用点 |
|---|---|---|
| **quality reasoning COUNT** | **248.9ms** | poolHealth（`LENGTH(reasoning)>0` 全表扫描） |
| **selfloop 全表扫描** | **94.1→71.6ms** | poolHealth（`src_kind=dst_kind AND src_id=dst_id`，无索引可用） |
| **srcCount 全表 GROUP BY** | **87.1ms** | poolApi questions（**每请求一次**！） |
| multiSource 全表 GROUP BY | 48.7→39.5ms | poolStats + poolHealth（**重复计算两次**） |
| orphan NOT EXISTS | 40.2→23.6ms | poolHealth |
| relTypes GROUP BY | 32.8ms | poolStats + poolHealth + relations（三处重复） |
| distinctQid / kadian / withImage | 6-8ms | 可接受 |
| FTS5 检索 | **13.5ms** | ✅ 本体极快 |

### 1.3 根因归纳

```
R44（结构性）: 统计型查询全表扫描，且【无缓存】——
              status/health/relations 三个端点各自全量重算一遍，
              同一份数据在一秒内被算 3 次（multiSource 算 2 次）。
R45（请求路径）: /api/pool/questions 每次抽题都跑 87ms 的 srcCount 全表 GROUP BY——
              「多出处加成」权重只需要「canonical_id 有几个源」，
              但每次请求都对 141489 行出处表做聚合。
R46（索引缺失）: selfloop/orphan 判据无索引可用（SQLite 对 OR/NOT EXISTS 的
              关联子查询只能全扫）。
R47（任务模型）: rebuild 是同步阻塞 HTTP 请求（220s）——HTTP 超时风险 +
              遥测 p95 被单次长任务污染（全局 p95=220850 全来自它）。
```

## 2. 优化方案（按收益排序）

| # | 方案 | 预期收益 | 代价 |
|---|---|---|---|
| O1 | **统计快照缓存**（表级 TTL：数据变更才失效） | status/health/relations 从 ~1000ms → **<5ms**（首查后） | 需要失效钩子（rebuild 完成时清） |
| O2 | **srcCount 预聚合表**（question_source 摄入时维护 `src_distinct` 计数到 question 表冗余列或缓存 Map） | questions 从 766ms → **<50ms** | 摄入时 +1 次 GROUP BY（一次性 87ms） |
| O3 | **selfloop/词表对账并入摄入期**（putRelation 已禁自环——运行期只需断言增量） | health -71ms | putRelation 已有守卫，运行期查询可降为LIMIT 1 探测 |
| O4 | **rebuild 异步作业化**（复用 repoManager 的作业模型：立即返回 jobId + 轮询） | 遥测不再被长任务污染；HTTP 不超时 | 中等改造 |
| O5 | reasoning COUNT 降采样 | health -200ms | ⚠️ 拒绝——统计必须精确（口径纪律），改用缓存（O1）后首查一次性成本可接受 |

## 3. 落地范围（本轮）

- **O1 全做**：`poolStatsCache`（Map<key, {data, builtAt}>，rebuild/增量重建后失效）——status/health/relations 共享同一快照。
- **O2 全做**：摄入时把 `COUNT(DISTINCT source_id)` 写进 question 表**已有冗余列**？——不：新列要 DDL 迁移（schema v3），改为**进程内 Map 缓存 + 摄入后重建**（与 O1 同一失效钩子）。
- **O3 全做**：selfloop 改为 `LIMIT 1` 存在性探测（putRelation 在写入侧已禁自环，运行期指标语义 = 「增量校验」而非「全量重算」）。
- **O4 部分做**：本轮先加 `maxFiles` 建议与文档（异步作业化留待下轮——作业模型改造涉及 repoManager 复用，超出本性能周期范围，登记 ROADMAP）。
- **O5 拒绝**：统计精确性优先（R06 不降级），由 O1 缓存消化成本。

## 4. 验收标准

1. `/api/pool/status`、`/api/pool/health` 二次查询 **< 50ms**（缓存命中路径）
2. `/api/pool/questions` **< 100ms**（srcCount 缓存命中）
3. `/api/pool/relations` **< 50ms**（poolStats 缓存命中）
4. 缓存失效正确：rebuild 完成后首查回到真实重算（快照 builtAt 更新）
5. 数字口径不变（缓存的只是**计算结果**，不是**采样值**——R06 不降级）
6. smoke 全绿 + 新增守卫

## 5. 中文思维

- **「账本天天记，报表月底出」**：流水（question/relation 行）是天天写的，报表（统计快照）是按需重算的——每来一个客人就把全年的账重新誊一遍，是账房先生的失职。缓存的不是真相，是真相的**最近一次誊写**；失效钩子保证誊写永远基于最新流水。
- **「秤要准，但不必每称一次都校一次砝码」**：reasoning 全表 COUNT 是「校砝码」级操作，249ms 一次可接受（首次），但每次称菜都校砝码就是 500ms 告警的来源。
- **「长活儿不站柜台」**：220 秒的 rebuild 站在 HTTP 柜台上，把整个柜台的平均接待时间拖成了 220 秒——这是**统计口径被单点污染**，不是柜台慢。异步化是下一轮的事，本轮先把这个信号**如实标注**（rebuild 的告警文案注明「长任务预期」）。

**实施记录（cycle-36）**：
- O1 统计快照缓存：`getCachedStats`/`invalidateStatsCache`（poolDb.ts）——status/health/relations 三端点共享，rebuild/review 写入后失效
- O2 srcCount 缓存：questions 的多出处加成权重预聚合（87ms/请求 → 命中 <0.1ms）
- O3a 自环存在性探测（71-94ms 全扫 → LIMIT 1）
- O3b **关系邻域单列索引**（ix_rel_src_id/ix_rel_dst_id，schema v3）——OR 查询 90ms → **0.5ms（180 倍）**，questions 端点 936ms→<50ms 的最大单项
- O3c **随机 rowid 采样**——无过滤候选查询的全表 ORDER BY RANDOM 215ms → 22ms（10 倍）
- O5 拒绝（统计精确性优先，缓存消化首查成本）——「秤要准，不必每次校砝码，但校过的砝码要留着用」
- 守卫落地形态：SMOKE-PERF-01..03 并入 smoke（见 §新增守卫实测结果）
